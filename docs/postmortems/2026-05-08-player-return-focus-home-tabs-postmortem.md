# 2026-05-08 播放器返回焦点与首页频道 Tabs 覆盖 Postmortem

## 结论

这次问题表面上是“从播放器返回后首页焦点回到了最上面的频道按钮”，
但真正根因不是首页单独写了一段把焦点强行拉回 tabs 的逻辑，而是：

1. 列表页进入播放器时，来源页原本会被卸载，导致列表状态和焦点一起丢失
2. 改成播放器覆盖层后，普通列表页已经能靠保活页面自然保住状态
3. 但首页仍然会回到 `个性推荐 | 正在关注 | 热门视频 ...` 这一排
4. 最终确认是“播放器返回焦点快照”在错误时机被提前消费，首页只是最先暴露这个问题的页面

最终修复不是给首页单独加特判，而是：

- 保留来源页挂载，只隐藏不卸载
- 进入播放器前显式记录当前内容区焦点
- 只有在播放器真正退出回来源页时，才消费这份焦点快照
- 左侧菜单重复点击当前页面时才触发刷新，而不是退出播放器自动刷新

## 用户可见症状

用户最初反馈分成两层：

1. 从视频播放退出后，列表会刷新，焦点回到列表第一位
2. 修完“列表不刷新”后，普通列表页已经能回到原位置，但首页仍然会回到顶部频道 tabs

第二层现象很容易误导判断，让人以为：首页自己还有一套单独的焦点覆盖逻辑。

## 根因一：播放器最初是路由切页，不是覆盖层

问题位置：

- `src/App.tsx`
- `src/components/AppShell.tsx`

最初从列表页进入播放器时，应用会直接把当前页替换成播放器页渲染。
这样做有两个直接后果：

1. 来源页组件被卸载
2. 列表的本地 state、滚动位置、section 的 `last-focused` 都一起丢失

所以“退出播放器后列表刷新、焦点回到顶部”并不是单一焦点 bug，而是页面生命周期设计就不对。

## 根因二：保活来源页后，首页仍然暴露出错误的焦点恢复时机

问题位置：

- `src/App.tsx`

把播放器改成覆盖层之后，来源页不再卸载。这样普通列表页已经基本恢复正常，因为：

- 列表数据还在
- 列表 section 也还在
- `enterTo="last-focused"` 通常足以把焦点带回原卡片

但首页和其它列表页不一样：首页顶部还有一个单独的内容区 section：

- `src/components/HomeChannelTabs.tsx`

这意味着一旦“显式焦点恢复”失败，首页的默认内容聚焦就更容易先落到这排 tabs，而不是下面的视频卡片。

## 根因三：焦点快照在进入播放器时就被提前消费了

问题位置：

- `src/App.tsx`

第一次补救时，我们已经加了“进入播放器前记录当前内容区 `focusId / sectionId`，退出时优先按快照恢复”。
方向是对的，但实现时机错了：

- 快照被记录下来了
- 但在进入播放器那次路由变化的自动聚焦流程里，它就已经被消费掉了

结果是：

1. 普通列表页即使快照失效，也还可能靠列表 section 的 `last-focused` 看起来恢复正常
2. 首页因为顶部 tabs 也是 content section，一旦快照没了，就会明显退回 tabs

所以首页并不是“额外多了一段错误逻辑”，而是它把“快照恢复时机不对”这个问题暴露得最明显。

## 修复方案

### 1. 把播放器改成覆盖层，来源页只隐藏不卸载

当前结构改成：

- 常规壳层继续保留来源页
- 播放器单独渲染在沉浸式壳层上方
- 退出播放器时直接回到仍然挂载的来源页实例

这样列表 state、滚动位置、分页状态和 section 焦点记忆都不会因为页面卸载而丢失。

### 2. 左侧菜单重复点击当前页面时才刷新

当前统一规则是：

- 从播放器返回来源页：不刷新列表
- 左侧菜单重复点击当前页面：主动触发刷新

这样体验上更接近电视端“继续从刚才位置接着看”的预期。

### 3. 焦点快照只在真正退出播放器时消费

这次最终修正的关键点是把焦点快照改成“两阶段协议”：

1. 进入播放器前只负责 `capture`
2. 退出播放器时再 `arm`
3. 回到来源页那一刻才允许 `restore`

这样可以避免：

- 进入播放器时就把快照吃掉
- 返回首页时只能退回默认 content section

## 为什么这个问题容易误判

这次最容易误判的点有两个：

1. 看到首页回到 tabs，很容易直接怀疑 `HomePage` 或 `HomeChannelTabs` 里有抢焦点逻辑
2. 看到其它列表页恢复正常，又容易误以为“全局恢复逻辑已经没问题，只差首页特判”

但真实情况是：

- 全局恢复逻辑当时仍然有 bug
- 首页只是因为顶部 tabs 本身也是一个 content section，所以最先暴露出了恢复时机错误

## 经验沉淀

后续继续做 TV 端路由、播放器和列表页时，必须保留下面这些约束：

1. 播放器这类沉浸式页面优先做覆盖层，不要默认卸载来源页。
2. “退出后保留原焦点”不能只依赖 section 自己的 `last-focused`，跨路由返回时应显式记录并恢复 `focusId`。
3. 焦点快照必须区分 `capture`、`arm restore`、`consume restore` 三个阶段，不能在进入目标页时提前消费。
4. 首页这类同时存在顶部切换器和内容网格的页面，是检验焦点恢复时机是否正确的高敏感场景。
5. 用户反馈“只有首页不对”时，不要立刻给首页加特判，先检查全局恢复链路是否只是被首页放大了。

## 验证与后续入口

这次修复后，至少验证了：

1. 左侧菜单重复点击当前页面时会刷新
2. 普通列表页进入播放器再返回，焦点能回到原卡片
3. 首页进入播放器再返回，不再退回顶部频道 tabs

后续如果再出现类似问题，排查顺序固定为：

1. 来源页是否真的被保活，没有在进入播放器时卸载
2. 进入播放器前是否记录到了正确的 `focusId / sectionId`
3. 这份快照是否只在播放器退出时才被 arm
4. 返回来源页时是否优先命中了记录的 card focus，而不是退回默认 content section
